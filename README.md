# 🦅 pgaero Workspace — ERP-система планирования КБ

Высокопроизводительный внутренний прототип трехуровневой системы оперативного планирования работ, контроля дедлайнов и учета трудозатрат авиационного КБ. Система спроектирована для развертывания на локальных серверах под управлением **ОС Windows** в полностью изолированном периметре безопасности (без доступа к сети Интернет).

Интерфейс системы унаследовал паттерны эргономики **Mailbird**: компактная левая панель навигационных иконок, широкое правое рабочее пространство, ленивая отрисовка контента в памяти Python и полное отсутствие сетевого оверхеда обеспечивают экстремальную скорость отклика (**latency < 20 мс**).

---

## 📐 3-Tier Planning & Priority Governance (Три уровня абстракции)

Иерархия данных в системе полностью нормализована и исключает дублирование:
`products` (Изделие) → `milestones_strategy` (Уровень 1: Стратегия) → `tactical_plans` (Уровень 2: Тактика) → `tasks_micro` (Уровень 3: Микроменеджмент) → `timesheet_monthly` (Месячная шахматка табеля).

### 🏆 Уровень 1: СТРАТЕГИЯ
*   **Бизнес-логика**: Используется дирекцией авиазавода. Показывает, завязана ли веха на жесткие штрафы Гособоронзаказа (ГОЗ). Срыв вехи со статусом `Критический (ГОЗ)` означает автоматическую остановку финансирования проекта.
*   **Механизм СУБД**: Прямая выборка вех (`milestones_strategy`) выбранного воздушного судна.
*   **Визуализация**: Еженедельный календарный Гант-таймлайн во всю ширину экрана с автоматической вертикальной подсветкой текущей недели сервера и выводом алармов.

### 🎯 Уровень 2: ТАКТИКА
*   **Бизнес-логика**: Используется начальником КБ. Выделяет отделы, находящиеся на Критическом пути. Если у «КО-2 (Прочность)» тактический план имеет приоритет `Критический путь`, то задержка их расчетов автоматически сдвигает сроки сдачи всего самолета вперед.
*   **Механизм СУБД**: Сбор данных по бюджетам отделов (`tactical_plans`), привязанных к соответствующим вехам.
*   **Визуализация**: Широкая кросс-матрица нагрузки (Pivot Table) КБ с автоматическим выводом распоряжений по критическому пути выполнения.

### 📋 Уровень 3: МИКРОМЕНЕДЖМЕНТ
*   **Бизнес-логика**: Используется начальником сектора и инженером. Помогает конструктору определить, за какой чертеж садиться утром. Задачи с приоритетом `Блокирующая` делаются в первую очередь, так как они останавливают работу смежных отделов.
*   **Механизм СУБД**: Получение оперативных задач (`tasks_micro`) инженеров через сквозную цепочку `JOIN` (Задачи → Тактические планы → Вехи → Проекты).
*   **Визуализация**: Плотная, удобная для сквозного осмотра таблица реестра задач, под которой развернута нативная, защищенная от ошибок React DOM календарная сетка месяца Mailbird (Month View Grid) и сводный табель экономиста (шахматка дней 1-31).

## ⚡ Алгоритм автоматической эскалации рисков (GOZ Bottlenecks)

Система связывает приоритеты всех трех уровней в единую шину риск-мониторинга КБ:
1. Инженер на **Уровне 3** отмечает задачу как `В работе` со статусом `Блокирующая`.
2. Функция `check_goz_bottlenecks` на бэкенде мгновенно протаскивает `JOIN`-цепочку к **Уровню 2** и проверяет, находится ли отдел на `Критическом пути`.
3. Если отдел на критическом пути, триггер уходит на **Уровень 1** к вехам с приоритетом `Критический (ГОЗ)`.
4. В правой панели Дирекция завода сразу видит корневую причину угрозы остановки финансирования всего самолета (с указанием ФИО конкретного инженера и характера блокирующей работы).

## 🔒 Механизмы отказоустойчивости и оптимизации Windows TCP

1.  **Железная ссылочная целостность**: Связи таблиц зафиксированы через `ON DELETE CASCADE`. При изменении структуры или аннулировании вех СУБД на уровне ядра мгновенно вычищает тактические подпланы и помесячные табели, предотвращая появление «записей-сирот».
2.  **Защита сокетов Windows**: В `config.py` внедрен кастомный `logging.Filter` для подавления системного мусора `_call_connection_lost` от разорванных браузерных веб-сокетов Windows, разгружая терминал PowerShell.
3.  **Реактивный сброс кэша**: Синхронизация табеля нижнего уровня вызывает принудительный `st.cache_data.clear()`. Это гарантирует, что руководство КБ увидит актуальный измененный прогресс на верхних уровнях без ручного обновления страниц.
4.  **SSO-Регистронезависимость**: Логины пользователей из `os.environ.get("USERNAME")` принудительно преобразуются в `.lower()`, защищая руководство от потери прав администрирования при разном написании системного аккаунта.

## 🚀 Порядок развертывания и пуска

1.  Убедитесь, что служба PostgreSQL запущена на локальном сервере (порт `5432`).
2.  Запустите консоль **PowerShell от имени администратора** (требуется для бинда портов локальной службы).
3.  Принудительно перейдите на целевой диск проекта через встроенный интерпретатор:
    ```powershell
    F:
    cd F:\sy\workspace\pgaero
    ```
4.  Выполните автоматический деплойер по абсолютному пути в обход системных ограничений `PATH`:
    ```powershell
    C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe -ExecutionPolicy Bypass -File .\deploy.ps1
    ```

Скрипт применит нативный Python-мигратор, полностью вычистит папки скрытого байт-кода `__pycache__`, отключит внешнюю телеметрию Streamlit (`--browser.gatherUsageStats false`) и запустит рабочее пространство по адресу: **`http://127.0.0.1:8501`**.
